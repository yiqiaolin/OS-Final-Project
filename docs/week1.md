## 01｜專題介紹

### 1.1 研究背景

作業系統與系統服務會產生大量日誌（System Logs），用來記錄程序活動、服務執行、身分驗證、錯誤訊息及其他系統事件。

系統管理員可以利用這些日誌了解系統運作情況，並調查可能的異常行為。

本專題選擇真實 Linux 系統日誌，透過 Python 進行資料解析、統計分析及視覺化，觀察系統活動與訊息模式，並嘗試將分析結果連結至作業系統相關概念。

### 1.2 研究目標

本專題預計達成以下目標：

1. 了解 Linux 系統日誌的資料結構與內容。
2. 將原始日誌轉換為可分析的結構化資料。
3. 分析程序活動、常見事件及時間分布。
4. 使用明確的規則調查可能的異常事件。
5. 將至少兩項分析發現連結至作業系統原理。
6. 建立可重現的分析流程與線上技術報告。

### 1.3 研究問題

正式研究問題將由小組根據資料探索結果決定。

目前候選方向包括：

- 程序與服務的日誌頻率
- 日誌活動的時間分布
- 常見訊息模式
- 錯誤相關事件
- 活動高峰
- 登入與身分驗證事件
- 稀有事件
- 程序與服務終止事件

**狀態：待小組選擇至少兩個可驗證的研究問題。**

### 2.3 日誌資料結構

一般 Linux 日誌可包含下列資訊：

| 欄位 | 英文 | 說明 |
|---|---|---|
| 時間戳記 | Timestamp | 事件記錄時間 |
| 主機名稱 | Hostname | 產生日誌的主機 |
| 程序標籤 | Process / Service Tag | 產生訊息的程序或服務 |
| 訊息內容 | Message | 系統事件的文字描述 |

例如，一般格式可以表示為：

```text
Month Day Time Hostname Process: Message
```

此為格式示意，並非從資料集中擷取的原始紀錄。

## 03｜資料處理與品質檢查

### 3.1 資料處理流程

目前已完成以下步驟：

1. 下載 Linux.log。
2. 建立原始資料副本 Linux_analysis.log。
3. 使用 SHA-256 驗證原始檔與副本的位元組內容一致。
4. 建立文字處理版本 Linux_processed.log。
5. 使用 Python 逐行讀取資料。
6. 依一般日誌格式初步解析欄位。
7. 將無法依一般規則解析的紀錄保留為特殊格式。
8. 統計程序、月份、訊息頻率及關鍵字。

### 3.2 使用工具

- Python
- collections.Counter
- hashlib
- shutil
- Git / GitHub

目前主要使用的分析腳本為 `check_log.py`。

### 3.3 解析方式

目前使用簡易規則進行欄位解析：

1. 以第一個 `: ` 分隔日誌標頭與訊息。
2. 將標頭依空白字元切分。
3. 將前三個欄位組合為時間戳記。
4. 讀取第四個欄位作為主機名稱。
5. 從第五個欄位擷取程序標籤。
6. 保留訊息內容。

若紀錄不符合上述規則，則標記為 `special`，保留該行文字。

此方式屬於初步探索用的啟發式解析器，正式分析前仍需檢查特殊格式及欄位準確性。

### 3.4 資料完整性檢查

Stored: 25567

- 沒有因初步解析失敗而直接丟棄整行紀錄。

但上述檢查不能保證所有欄位內容都正確。

### 4.4 低頻率訊息

若選擇稀有事件分析，需要先處理訊息中的動態欄位，避免將普通事件誤判為稀有事件。

- 不同程序的候選錯誤事件比較
- 活動高峰與一般時段比較
- 驗證事件類別比較

### 7.3 異常事件調查

依照老師要求，異常調查必須使用明確的啟發式或統計規則。

可能方法：

- 低頻事件篩選
- 每小時或每日事件數量門檻
- 與一般時段相比的活動高峰
- 特定錯誤相關事件的集中出現

若資料缺乏真實標籤，僅能討論疑似異常，不應宣稱已確認故障。

正式分析還需要檢查具體的事件序列。

### 7.5 作業系統理論連結

預計至少選擇兩項分析發現，連結至作業系統概念。

可能主題：

- System Logging：系統日誌與監控
- Process Management：程序管理與生命週期
- System Services：系統服務
- Authentication：身分驗證
- Error Handling：錯誤處理
- Reliability：系統可靠性

分析時應明確區分日誌能直接證明的事實與推測。

例如，日誌數量增加不能直接證明 CPU 使用率增加；錯誤關鍵字出現也不能直接證明系統故障。
